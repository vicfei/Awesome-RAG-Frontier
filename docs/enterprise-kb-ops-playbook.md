# 企业知识库运维实战手册（v0.1）：从上线到扛住生产

> 姊妹篇：[enterprise-kb-playbook.md](./enterprise-kb-playbook.md)（选型与知识形态）。本篇补上它没写的另一半——**部署、验收、排障、治理的工程实操**。
> 来源声明：以下经验出自一次完整的企业落地（开源 RAG 引擎 fork + 私有化部署 + 多模型平台对接 + 智能体沙箱），全部经过生产实弹验证；环境细节已脱敏为通用形态（"测试环境/生产环境/共享 GPU 节点"）。标注〔实测〕的数字为当次环境观测值，供方法论参考而非性能承诺。

## 一、部署验收：三级铁律（最容易死人的地方）

**核心认知：健康检查证明"活着"，不证明"换了"。** 三级递进的验收锚点〔实测三次拦截假成功〕：

1. **活着**：健康端点 200 / 横幅正常——只排除"起不来"；
2. **同 daemon 锚**：比对容器 `docker inspect --format '{{.Image}}'` 与预期镜像 ID——排除"标签对内容错"；
3. **跨节点锚层指纹**：`docker inspect <镜像> --format '{{join .RootFS.Layers ","}}' | sha256sum` 与构建侧基准比对——**同一 tar 在不同 docker daemon load 会得到不同 image ID**（存储布局差异），只有层指纹跨 daemon 不说谎。

配套纪律：**回滚锚点先行**（升级前记录现役镜像 ID/具名 tag，回滚=tag 指针反向+up，分钟级，数据面零动作）；`up -d` 的幂等空转 ≠ 重启——**没有 Recreating/Started 字样就是没换**〔实测两次踩中〕。

## 二、零迁移升级与交付链

- **镜像指针法**：compose 引用名不动，`docker tag 新镜像 引用名` + `up -d` 即升级；反向 tag 即回滚。文件与数据面全程不碰〔实测单版本升级窗口≈重建一个容器的时间〕。
- **离线交付链**（内网无外网场景）：tar + sha256 双端校验 → **分档去重**（8 镜像单档 save 比逐镜像分档省 2/3 体积〔实测 1.8G→602M〕）→ 回收侧 load 回测；宿主侧资产（systemd 单元在 `/etc/systemd/system` 不在应用目录——**容易漏打包**〔实测〕）。
- **OCR/截图转录的防御**：远端输出经转录回传时，哈希类长串易缺字符——终验改"节点本地比对、只回传 0/1"（`... | sha256sum | grep -c <期望值>`）〔实测拦截一次转录丢字〕。

## 三、生产数据面取证

- **甄别"摆设容器"**：本地 DB 容器在跑 ≠ 应用在用它。实证链：应用 `printenv DB_HOST` → 本地库数据新鲜度 → role 存在性。〔实测：生产库实为外部托管实例，本地容器为陈旧摆设——修正了整个运维口径〕
- **UPDATE 0 顺藤摸瓜**：批量 UPDATE 命中 0 行往往是"连错库"而非"条件错"。
- **异步聚合计数的时延**：上传/删除后立即查 count 不可靠（瞬时拿到未刷新值），验收要用文档存在性而非计数。

## 四、积压治理（一次 2.1 万档的清零实战）

1. **法医式取证先行**：按 status 分布 + per-status 的 updated_at min/max（时钟指纹）把积压分段归因——区分"正在消化"与"历史伤亡"〔实测发现 53% corpus 的 failed 积压从未入账〕；
2. **接口考古三验**：批量接口的路由挂载点以源码为准（文档/记忆里的路径可能是不存在的路由）；注意 handler 级硬顶（如 200 ids/批）；注意鉴权模型（跨租户默认关）；
3. **幂等补发**：重发工具按"完成态跳过"设计，可安全重跑补刀〔实测 108 批 21,437 档全清〕。

## 五、元数据悬空：升级后"功能坏了"的第一嫌疑

版本升级后新功能报"实体不存在"类错误，**先查旧版本遗留的悬空引用再查新代码**：树形/标签类结构里旧绑定指向已删除的实体行，查询时解析失败。快速判别法：同一部署在新建数据上一切正常、仅旧数据报错〔实测：悬空 tag_id，删除重建即愈〕。反向启示：**删除类操作要有影响预览**（显示将影响的文档数），这正是防悬空产生的最好设计。

## 六、解析引擎集成：版本代差是分维度的

以 MinerU 为例〔实测 2.2.x 部署 vs 上游 4.x〕：

| 维度 | 代差影响 |
|---|---|
| 纯文本抽取 | 小 |
| 表格/公式 | 大（VLM 后端跨代提升明显）|
| OCR/扫描件 | 大（3.4 换代 OCR 引擎 +11%〔上游口径〕）|
| API 契约 | 跨大版本要回归（参数面/端点可能变）|

**VLM 档激活三层检查法**：引擎包在不在容器里（`backend=engine` 报 not installed=镜像缺包）/ client 模式有没有 server_url 参数通道 / 权重在不在本容器。同 pod 部署了推理容器但两头没接线是最常见的静默缺口〔实测〕。

## 七、LLM 平台对接：画像先于优化，经济学先于架构

- **画像法**：/metrics 分钟级采集（running/waiting）+ pod 侧全参数取证（cmdline/environ/权重目录日期戳）+ `/version`、`/v1/models` 巡检通道——一套动作产出引擎/权重/量化/别名五列台账。
- **两个实测教训**：①GPU util 100% ≠ 请求拥塞（kernel 忙与排队是两回事，容量决策要看请求级 running/waiting）；②**路由/分流收益 = 车道差 − 决策成本**：低资源对照实验（40 题 × 快慢双档 × 路由/直连四配置）中，CPU 决策开销 ~1.5-2s/请求远超双档时延差 0.19s，路由总时延反超直连强档 39%——**没有拥塞就没有分流收益**，先量化再上架构。
- **无鉴权流量的归因困境**：共享网关后"谁吃掉了容量"不可归因，需要网关日志/采样配合——接入路由前先解决可观测性。

## 八、智能体沙箱上线决策矩阵

| 判据 | Docker 沙箱（可信代码）| MicroVM 沙箱（强隔离）|
|---|---|---|
| 硬门槛 | docker ≥24 | **嵌套虚拟化/KVM**（企业 VM 常默认不开——一票否决项，其余资源再富余也没用〔实测〕）|
| 治理 | docker.sock=宿主 root 级能力下放，多服务共存宿主要评估 | 内核级隔离，面更小 |
| 镜像契约 | uid1000 user + /workspace/{input,output} 归属 + GNU find/timeout + 以 USER user 结尾 | 平台托管 |

微镜像设计取舍〔实测 80MB 级〕：curl（连通检查硬依赖）、压缩工具（技能包解压）、uv（venv 提速）不能省；node 视技能需求。**预设智能体 ≠ 通用智能体**：专业预设绑固定工具链不带技能运行时，点火失败先查"通用智能体+沙箱访问开关"再查模型。
